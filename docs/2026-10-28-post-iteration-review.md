## 汇总定级与可复现结果

### P2：设置页选收藏后，键盘焦点丢失

两款均确认。选择数据成功，但生产后台写入 reading_state_v2 后，Options 的 load → list → replaceChildren 重建收藏和最近列表，把当前按钮移出 DOM。主线程在浏览器运行未改的生产 background.js 与 options.js，只适配消息和存储 API：

- 聚焦第二条选择按钮，按 Enter。
- 观察到后台状态写入 1 次、原按钮 isConnected=false、activeElement=BODY。
- 下一次 Tab 回到第一条。具体后续 Tab 顺序可能随环境不同，但焦点节点被销毁已确认。

这是基线遗留的设置页路径；上一轮主要修复页面画廊入口的焦点，未覆盖它。原轻量夹具的 reading 操作只更新闭包 state，不发生产后台的状态存储通知，因此此前 49 项断言中的“键盘选择成功”漏掉了这个中间事件。

**建议修正/验收：** 对未变化条目保留 DOM 身份；若重建，按区域、内容 ID 与控件类型保留合理焦点；用户已主动移到别处时不抢回。验收检查实际后台通知之后的 activeElement 和下一次 Tab，包括收藏/最近同 ID 以及删除条目。

### P2：无当前内容的首载缺少等待反馈

两款 × 指针/键盘共四组均确认。让 requestContent 延迟 3 秒，并关闭悬停展开以隔离触发路径。约 1 秒时：

| 进入方式 | 观察 |
| --- | --- |
| 指针点击 | session 已开始，画廊仍 hidden，入口仍显示，没有准备提示 |
| 键盘 Enter | 空展厅已显示并接到焦点，但 status / updateStatus 均为空 |

四组最终均正常载入，**不是卡死或永久白屏**。这是首次内容请求阶段的反馈缺口；手动“下一条/幅”已有内容时的稳定等待仍成立。

**建议修正/验收：** 首次主动进入立即给出轻量、可播报的准备状态，成功/失败/关闭均正确结束；继续保留自动展示不抢 AI 输入焦点。覆盖冷首载、请求失败以及关闭后的迟到结果。

### P3：消费选择后，“已选，下次打开”仍可能指旧内容

两位评审对严重度不同：Emil 为 P2，Lama 为 P3。汇总按 **P3 状态提示问题** 安排：内容切换与继续观看本身正常，失准的是对下一次打开的承诺，且可通过重新选择恢复。

Wiki 完整受控浏览器链已确认：选 A（postreview1）→打开 A→真实更多菜单换到 B（1xvv34o）→关闭重开仍 B。此时 pendingSelection=null，存储标记仍为 A，设置仍把 A 标成“已选，下次打开”。

该链路使用真实后台、Companion、Options 与读取本地 CSV 的 provider；仅 Chrome API 为替身，两页之间手动中继状态和标记以模拟同一个 Chrome.local。Art 代码相同，另有只读 VM 证据，本轮未重复 Art 的完整消费浏览器链。

**建议修正/验收：** 明确它表达“待打开选择”还是“上次选择”。按现有“下次”含义，应在消费后取消待打开提示，并防止旧确认抹掉较新的选择；若表达历史，修改文案。不要改变已确认的当前内容保留或随机策略。

- 画廊入口 Enter/空格有落点，关闭返回入口；更多菜单先单独响应 Esc。

- Art 与 Wiki 的观看/阅读文案、24/1 场景差异与独立产品定位成立。
- 当前截图没有额外白色正文底板；窄屏暗色布局与减少动效的既有证据继续保留。

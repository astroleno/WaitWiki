# ArtBreeze / WaitWiki 本轮迭代后的 Emil 独立复核

日期：2026-10-28。采用本地 `emil` 的 `emil-design-eng` 主路线，关注输入、焦点、状态反馈、取消、空间连续性和使用心流。本报告是审阅；下文问题表的 **After 均为建议验收目标，不表示已经实现**。

## 结论

本轮修改方向成立。主动键盘进入、Esc 分层关闭、换内容时保留旧空间、Art 候选图预解码，以及阅读收藏摘录，均与“等待时短暂停留，随时回到 AI 对话”的使用方式一致。没有发现 P0 / P1，也没有理由因系列重叠、默认 2 秒、九类随机内容或没有新增装饰动效阻断本轮。

保留两项 P2：收藏列表在真实存储变更链上会销毁当前聚焦控件；新选中提示没有与选择的消费生命周期保持一致。列表焦点问题经独立源码分析后，由主线程补充两款浏览器复现；选择消费后的状态不一致经源码与只读 VM 确认后，主线程又补充了 Wiki 的完整浏览器交互链。

**可以继续准备送审材料；建议先处理这两项状态与键盘连续性问题，再把当前 UI 记为最终验收通过。** 本结论只评价当前实现与证据，不保证 Google 审核结果。

## 保留的问题

### E1 · P2 · 存储刷新会销毁收藏列表的键盘焦点锚点

| Before | After | Why |
| --- | --- | --- |
| 按下收藏或最近内容的“下次读这条 / 下次看这幅”后，后台 `select` 写入 `reading_state_v2`；Options 监听该变化并用 `replaceChildren()` 重建两个列表，当前聚焦按钮随旧行一起被移除。列表重建没有保存或恢复焦点。 | 更新列表时保留仍存在条目的 DOM 身份；或在确有重建必要时，按“列表区域 + 内容 ID + 操作”恢复到相同控件。仅在条目被删除时提供明确的相邻落点。 | 选择状态虽能保留，用户继续按 Tab 的位置却可能丢失。键盘操作应能从刚刚选择的条目自然继续，而不是重新寻找该条目。 |

**位置：** 两端 `options.js:18–19、25–26、42–54`，后台触发链为 `background.js:24–29`。这是基线已经存在、当前仍未解决的路径，不是本次新增 `selectionRevision` 本身造成的回归。

**触发：** 设置页用 Tab 聚焦第二条收藏中的选择按钮，按 Enter / 空格，等待后台写存储和后续 `load()` 完成。即使本次选择成功，原按钮也会因列表重建而断开连接；其他标签页的阅读记录或进度变化同样可能触发刷新。

**影响与证据状态：** 已确认。独立源码分析确认聚焦节点会被销毁；主线程随后在两款的浏览器路径上补测：未修改生产 `background.js` 和 `options.js`，通过页面内 API 适配让消息真实经过 `dispatch → reading → storage.local.set`，观察到一次状态写入后旧按钮 `isConnected=false`、`activeElement=BODY`，下一次 Tab 回到第一条。这是生产代码加 API 替身的复现，非原生扩展安装。现有夹具 `tests/fixture-chrome.js:22–24` 对 reading 操作只更新闭包 `state`，没有模拟生产后台的 `reading_state_v2` 存储事件，因此已有“键盘选择成功”的断言没有覆盖这条链。

补充界面证据为 [主线程的选择后列表截图](assets/2026-10-28-post-review-library-focus.png)，本评审也已通过 `view_image` 查看。焦点结论来自运行观察，不能仅凭静态截图推定。

**修复验收：** 用包含生产后台存储事件的路径选择一条收藏，等待所有刷新后，焦点仍位于该行选择控件，且“已选”状态正确；下一次 Tab 到该行下一项操作。取消收藏和同时存在于收藏/最近两个区域的同 ID 条目，也应保持可预测的焦点落点。刷新发生期间若用户已主动移到别处，不得再把焦点抢回。

### E2 · P2 · “已选，下次打开”在选择消费后仍作出失实承诺

| Before | After | Why |
| --- | --- | --- |
| Options 把持久化的 `reading_selection_v2.id` 一直解释为“已选，下次打开”。Companion 首次打开后只清除实例内的 `pendingSelection`；选项页的标记仍存在。之后换到 B、关闭再开时显示 B，但 A 仍标为“已选，下次打开”。 | 让选中标记与真实消费规则一致：消费后不再显示仍待打开的承诺；若需要保留历史选择，则明确写成历史状态。新选择不能被旧一次消费确认覆盖。 | 新增的文字与 `aria-pressed` 让用户相信 A 仍决定下一次打开内容，实际打开却遵循当前 B。视觉反馈不能比底层状态更肯定。 |

**位置：** 两端 `options.js:5–10、25–26、42–54`；`gallery/companion.js:99、215–225`。底层一次性消费逻辑来自基线，本轮新增的持续“已选，下次打开”反馈暴露了这项语义不一致。

**触发：** 在设置页选择 A → 回到已加载的 AI 网页打开入口，显示 A → 更多菜单换到 B → 关闭并重开 → 回看设置页 A 的状态。

**影响与证据状态：** 已确认。独立 VM 使用真实 `Companion.open()`、`next()`、`Session`，得到显示序列 `[A, B, B]`，同时 `pendingSelection = null`、持久选择标记仍为 A，整个路径没有清除或确认该标记。

主线程随后用 Wiki 的完整浏览器链补证：设置选 A（`postreview1`）→ 入口显示 A → 操作真实更多菜单“换一条”到 B（`1xvv34o`）→ 关闭重开仍为 B；设置页仍把 A 标为“已选，下次打开”，`pendingSelection=null`，存储的 `reading_selection_v2` 仍为 A。补测未修改生产后台、Companion 或 Options，通过 Chrome API 替身运行；两页之间手动中继状态与标记以模拟 `Chrome.local` 共用，gathas 使用真实 provider 读取本地 CSV，没有外部内容请求。Wiki 的可见文案与实际下一次打开不一致已在浏览器确认；Art 使用相同共享代码，但本轮没有重复其完整选择消费浏览器链，不把代码同一性写成 Art 浏览器实测。

已查看 [主线程补充的选择标记截图](assets/2026-10-28-post-review-selection-marker.png)。该补证仍不属于原生安装或真实 AI 发送验证。

**修复验收：** 上述序列走完后，设置页不能继续承诺“下次打开 A”；显示状态应准确反映当前规则。补测 A、B 两次快速选择以及旧异步列表读取，确保旧确认或旧读取不会抹掉较新的选择。无需改动已确认的随机内容策略。

## 视觉与动效判断

五张当前截图支持既定方向：Art 保持独立居中画作和右侧两行墙签；Wiki 文字直接在固定 bg-027 墙面上，390px 暗色截图未见额外白色正文底板或面板横向越界。加载提示没有以整面遮挡替换旧内容，收藏摘录能直接区分同名偈语。

本轮没有引入新的位移或复杂过渡。现有 180ms 面板进入、150ms 工具显隐和 reduced-motion 规则均在源码中；不把缺少新动画或未重做既有短动画列为本轮阻断。静态截图不能证明过渡每一帧或真实宿主页的焦点行为。

补充观察，不新增严重度条目：主线程对两款无已保存内容的冷首载，分别以指针与键盘进入并控制响应为 3 秒。在第 1 秒，指针路径仅见入口，键盘路径出现空展厅，两处 status 均为空；最终均成功载入。这说明本轮 `next()` 的等待反馈没有覆盖无旧内容的首载阶段，后续首载验收应单独核对响应提示。这里的 3 秒为受控延迟，不是对真实内容接口速度的判断。

本次新增测试结果为两端各 36/36；已有 49 项浏览器断言来自生产 UI 开发夹具、Chrome API 与内容替身。尚未获得本次原生扩展安装、真实 AI 发送、浏览器缩放或屏幕阅读器播报证据，不能由这些测试推定上述场景也已经通过。
